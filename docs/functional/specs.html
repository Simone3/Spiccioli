01

Premise and constraints

  • One user, one machine, one file. No accounts, no server, no sync logic.
  • A desktop application on macOS, Windows and Linux. All three are first-class: the same build behaves identically on each, and nothing may depend on a platform-specific path, filesystem behaviour or system service. No mobile, no web deployment (§14).
  • Nothing leaves the machine except, optionally and only when explicitly triggered, security identifiers sent to a price provider (§8.4).
  • Euro only. Currency is recorded on accounts and securities but every computation assumes EUR. No exchange rates, no conversion.
  • English only. The interface ships in one language and there is no language selector. Nothing user-facing may be hard-coded in a way that would make a second language a rewrite: strings stay separable from the code, and dates, decimal separators and currency already come from preferences rather than a system locale (§11.4).
  • Dark theme only.
  • The application replaces a spreadsheet holding ten years of history. Data entry speed and the ability to spot a mistake matter more than features.
  • Derived data is never stored. Balances, holdings, averages, totals and pairings are computed from records. The only manual figures are the ones no record can produce: prices, and the default sell fee per institution.
The organising principle. Two independent sources of truth are kept deliberately unlinked — bank transactions come from account exports, trades and payslips are entered by hand — and the application's job is to tell you when they disagree. That is why nothing is auto-generated from anything else, and why §10 exists.

4.1 Behaviour

  • Failing-check banner. Shown whenever any check fails, above everything else, naming each failing check in one line and linking to §10. Absent when all pass.
  • Net worth = Σ account balances + Σ holding market values (§12.4). Holdings are valued at their latest known price, gross — no hypothetical tax or fee is deducted from the headline figure.
  • The three figures beneath it are that total taken apart. Sum of all transactions is the same net worth with holdings valued at cost instead of at price, so unrealised investment gain is exactly the difference between the two. …net, if sold today then restates that gain after the hypothetical tax and sell fees of §12.3, summed across every holding — the only figure on the screen that answers what the portfolio is actually worth in hand. It sits below the gross gain rather than replacing it because it is an estimate resting on average-cost lot matching, and carries the §12.3 caveat on hover.
  • All-time figures are lifetime sums of the named categories, plus realised gain from sales (§12.2).
  • Breakdown by type. Account balances contribute under the account's type; holdings contribute under their security's type, at market value, consistently with net worth. An account holding securities therefore appears as Liquidity for its cash only, never as a slice of its own. Closed accounts are excluded.
  • The pie carries one slice per type, sized by its share of net worth, with the type count at its centre and the same colour keying the list beside it. It exists to make the shape of the portfolio readable at a glance; the list beside it carries the amounts and percentages.
  • Net worth over time, monthly points, §12.5. The stretch before the first recorded price is drawn dashed and labelled as cost-based.
  • Accounts table lists open accounts with computed balances. Read-only; accounts are created and edited in Settings (§11).

5.1 Columns

  • Category chip is violet when categorySource = rule, neutral when manual, red when empty. Violet denotes provenance, not correctness — deliberately not green.
  • Matched is derived and read-only: the counterpart account for a paired internal transfer, the security for a trade-matched securities transaction, an em dash otherwise (§12.6).
  • Notes is free text the user owns. The application never writes to it.
  • Receipt cycles unchecked → checked → na.
  • The footer sums the filtered rows, across all pages.

5.2 Ordering and paging

  • Always date ASC, insertionSeq ASC, id ASC. Columns are not sortable and the order is not configurable — the list must look identical every time it is opened.
  • 50 rows per page. This is the only paginated table in the application; every other table is shown in full.

5.3 Filters

Account · period · category · amount range · receipt state · free-text search on description. Combined with AND. Filters affect the footer totals and the page count.

5.4 Editing

  • Every cell is editable in place — date, account, description, amount, category, receipt state, notes. Click to edit.
  • Setting a category by hand sets categorySource = manual, which protects it from every automatic re-categorisation.
  • This is reversible. The category picker offers a special entry — Automatic (let rules decide) — at the top of the list. Choosing it sets categorySource back to rule and immediately re-applies the rule list to that transaction, leaving the category empty if no rule matches. There is no state a hand-edit can trap a row in.
  • Row menu: duplicate, delete. Delete asks for confirmation — there is no undo.
  • Apply rules to uncategorised runs the rule list over transactions with no category. It never touches a categorised row.

Duplicates

  • Exact match on account + date + amount + normalised description against transactions already in the file. Normalisation: trim, collapse whitespace, case-fold.

8.4 Prices

  • Prices are entered per security with an as-of date, and every value is kept as history. Editing a price adds a record; it does not replace one.
  • Optional online lookup is disabled by default. When enabled in Settings, it is triggered only by the explicit Update prices button. Never automatic, never on load.
  • It sends security identifiers — ISIN or ticker — to the configured provider. No amounts, quantities or account data ever leave the machine. The application must state this where the feature is enabled.
  • Fetched values are shown for confirmation before being written as source = fetched Price records.
  • The application is fully usable with the feature off. A provider failure is a message, never a blocked screen.

12

Calculations

Every formula in one place. All amounts are EUR; rounding is to 2 decimals at display, never in intermediate steps.

12.1 Weighted average cost

  • Per (security, account), walking trades in date order.
  • Purchase: quantity += q, costBasis += q × price + fees, avgCost = costBasis ÷ quantity.
  • Sale: quantity −= q, costBasis −= q × avgCost. avgCost is unchanged by a sale.
  • Fees increase the cost basis on purchase and reduce proceeds on sale. Taxes withheld on a sale never touch the cost basis — they leave the proceeds, not the position.

12.2 Realised gain on a sale

  • netProceeds = q × price − taxes − fees — the trade's total, and the figure compared against the bank transaction by check 7.
  • realisedGain = netProceeds − (q × avgCost at the time of the sale). Net of everything the broker took, so it is what the sale actually added to net worth.
  • Summed across all sales for the Portfolio all-time figure.
  • The gross counterpart, q × price − fees − (q × avgCost), is what the tax was computed on. It is not displayed: the tax on a real sale is a recorded fact, so there is nothing to reconcile it against.

12.3 Hypothetical liquidation

  • grossProceeds = quantity × price
  • gainBeforeTax = grossProceeds − (quantity × avgCost)
  • tax = gainBeforeTax > 0 ? gainBeforeTax × taxRate(security.type) : 0 — never negative; a loss produces no rebate.
  • fee = institution.defaultSellFee of the holding's account
  • netProceeds = grossProceeds − tax − fee
  • netGain = netProceeds − (quantity × avgCost)
  • The portfolio-level figure is the sum across all holdings, each with its own institution fee and tax rate. This sum is the …net, if sold today line on Portfolio (§4.1).
  • Applies only to open holdings. A sale that has happened carries the tax the broker actually withheld (§2, §12.2); this section never restates it.
Weighted average is an approximation. A broker may match lots differently when computing the taxable gain, so the tax figure is an estimate. The application must say so wherever the figure appears.
Room for another tax system. Only the Italian one is implemented, and the shape above is deliberately the smallest that can hold a different one: the rate is a parameter per security type (§11.4), not a constant; the gain it applies to is computed separately from the rate applied to it; and tax appears in exactly two places — this hypothetical, and the recorded figure on a sale. Whitelist government bonds already exercise the mechanism at 12,5%. Anything a future regime needs beyond a rate per type — holding-period relief, loss carry-forward, a personal allowance — is a change to this section alone, not to the domain model, and is not designed for now.

12.4 Balances and net worth

  • accountBalance = openingBalance + Σ transaction amounts
  • netWorth = Σ accountBalance (open accounts) + Σ holding marketValue
  • Securities purchases already reduce the cash account through their transaction, so holdings are added, not double-counted.

12.5 Net worth over time

  • Monthly points at each month end, from the earliest transaction to today.
  • At date d: Σ (openingBalance + Σ transactions ≤ d) plus, per holding, quantity(d) × price where price is the most recent Price record dated ≤ d.
  • If no price is known at d, the holding is valued at avgCost(d). That stretch of the line is drawn dashed and labelled cost-based.

12.6 Derived matching

Records that ought to correspond are paired heuristically, with no linking effort from the user. Matching is recomputed, never stored.

  • Internal transfer legs: equal absolute amount, opposite signs, different accounts, dates within transferMatchWindowDays, both categorised Internal transfer. Greedy one-to-one, nearest date first. Unpaired legs are listed by check 1.
  • Trades against transactions: a Securities purchase / Securities sale transaction pairs with a trade of the matching kind when the absolute amount equals the trade total, the account matches, and dates are within tradeMatchWindowDays. One-to-one. Unmatched records on either side are listed by checks 6 and 7.
  • The trade total is the one from §2 — qty × price + fees on a purchase, qty × price − taxes − fees on a sale. Both are the figure that moved through the account, which is why the comparison is an exact amount match and not a tolerance.

12.7 Salary figures

  • netSalary = netPayment − refunds + carPayment
  • netGrossPct = netSalary ÷ gross
  • yearContractGross = max(contractGross in year) × contract.monthsPerYear
  • grossPerHour = Σ gross in year ÷ (workingDays × contract.hoursPerDay), and the same with Σ netSalary.
  • All of the above are computed within the selected contract only.
13

Storage

  • One file holding everything: institutions, accounts, securities, prices, transactions, trades, contracts, payslips, rules, preferences.
  • The file lives wherever the user puts it — a plain local folder, a cloud-synced folder, or an encrypted vault inside one. The application makes no assumption about the location and requires nothing of it.
  • Autosave, debounced, written atomically — write to a temporary file in the same directory, then rename — so an interrupted write cannot truncate it.
  • External modification detection. Before writing, the application verifies the file has not changed on disk since it last read it. If it has, it warns rather than overwriting.
  • Ten rolling timestamped backups in a folder beside the data file, count configurable.
  • On launch the application always asks which file to open, offering the recently opened locations. It never reopens the last file automatically.
  • No undo/redo in v1. This is why every delete confirms.
  • The format must be documented well enough for an external script to write it — the ten years of historical data will be loaded by a one-off migration script, not by the application.
  • The application must refuse to silently drop a category or field it does not recognise in a file, since the category list is fixed in the application and files may outlive a version.
Atomic writes and external-modification detection are not paranoia about a specific setup: they are what makes the file safe in a folder that something else — a sync client, a backup agent, an encrypted volume — may also be touching. They cost little and they are the reason the application does not care where the file is.
